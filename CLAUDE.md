# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Smart Astro Planner (SAP) is a single-file PWA for astrophotography planning. It uses a local catalog of 19,092 deep sky objects for target selection, real sky images (HiPS2FITS) for framing, and the Claude API (optional) for plans and descriptions. Deployed via SFTP to Namecheap shared hosting at `/public_html/smart-astro-planner/`.

**Purpose (keep design decisions consistent with this)**: SAP answers *"what are my options over the next few weeks?"* from an amateur's backyard (partial horizon, few clear nights, limited hours per target) — NOT *"what can I shoot tonight?"* and it does not compete with Telescopius/SkySafari. Users are expected to validate in other tools before committing several nights. The help page's "What is Smart Astro Planner?" section states this; do not drift from it.

## Architecture

**Single-file app**: All HTML, CSS, and JS are in `index.html`. No build step, no framework, no dependencies.

**Supporting files**: `astronomy.browser.min.js` (astronomy-engine 2.1.19 by Don Cross, MIT, self-hosted with its license header intact — it powers every visibility/altitude/transit calculation; it used to load from the jsDelivr CDN with `@2`, but the service worker never caches cross-origin scripts and jsDelivr's `@2` range only has a 7-day HTTP cache, so offline use in the field could lose it. To upgrade, download the exact new version, replace the file, and bump the `?v=` in both `index.html` and the `sw.js` ASSETS entry), `manifest.json` (PWA manifest; `start_url` is deliberately the relative `"./"`, not `/smart-astro-planner/`, so a fork hosted in any folder can be installed; `sw.js` caches it cache-first, so any change to it needs a `CACHE_NAME` bump), `sw.js` (service worker, see below), `catalog.json` (local object database, ~2.8 MB), `build_catalog.py` (one-time script to regenerate catalog from VizieR/OpenNGC), `icon-192.png`, `icon-512.png`, `help.html` (standalone help page with own CSS, loaded in iframe), `.htaccess` (forces no-cache on `sw.js` on the Namecheap host), `index.html.backup` (old snapshot, ignore; git-ignored), plus `README.md`, `LICENSE`, `LICENSE-CATALOG`, `THIRD-PARTY-NOTICES.md` and `.gitignore` (see Licensing below).

**Service worker (`sw.js`)**: network-first for same-origin HTML, cache-first for other same-origin assets, pre-caches `catalog.json?v=5`, `astronomy.browser.min.js?v=2.1.19` and `help.html?v=X`. Cross-origin requests are NOT cached (early `return`) except images from `alasky.cds.unistra.fr` and `upload.wikimedia.org`, which go to a separate cache `sap-images` (re-fetched in `cors` mode so entries are non-opaque and measurable; max 80 entries, oldest evicted, re-inserted on hit to approximate LRU; the `activate` handler must keep `IMG_CACHE`). **Every deploy: bump `CACHE_NAME` in `sw.js`** (and, for anything a user can notice, add an entry at the top of the Change Log in `help.html` under a new date heading and set `APP_VERSION` in `index.html` to that date — the owner has no way to know who uses the app, so the Change Log is how users learn what changed; keep entries short, user-facing and in English, no code names) or installed PWAs won't update (Mac PWA sometimes also needs right-click → Refresh). Settings → Preferences shows the image cache count/size with a Clear button (`updateImageCacheInfo()`, `clearImageCache()`).

**7-tab structure** (bottom nav): Targets → My Targets → Equipment → Locations → Night Info → Settings → Help. Each tab renders dynamically via `render*()` functions (Night Info's internal id/function is still `meridian` / `renderMeridian()`; My Targets' internal id/tab/renderer are likewise still `plan` / `#tab-plan` / `renderMyTargets()`, a holdover from when this tab generated session plans). Modals and detail screens use `position:fixed` overlays.

**Data**: localStorage for user data (keys prefixed `sap_`), in-memory for catalog (`SAP_CATALOG` global, loaded via fetch at init). State helpers: `LS.get(key, default)` / `LS.set(key, value)` with JSON serialization. Main keys: `sap_locations` (each has `min_altitude`, `horizon_sectors`, `updated_at`), `sap_equipment`, `sap_meridian` (Night Info targets), `sap_mytargets` (saved framings, see My Targets below), `sap_saved_queries`, `sap_saved_lists`, `sap_targets` / `sap_target_meta` (active search-result list), `sap_preferences` (`detail`, `listSize`, `wiki`, `skyview`, `skySurvey`, `moonThresholds`), `sap_lines` (emission analyses per catalog ID), `sap_ai_desc` (AI descriptions per catalog ID), `sap_last_export` / `sap_last_import`, `sap_mode`, `sap_claude_key`. Items that sync carry `updated_at` (ISO string).

**AI integration** (optional, "assisted" mode = API key set): (1) per-target "AI Description" card (`askClaudeAboutTarget()`, prompt in `buildTargetInfoPrompt()`, cached in `sap_ai_desc` keyed by catalog ID; common name + imaging tips, instructed not to invent names), (2) "Capture Advice" card on a My Targets entry (`askCaptureAdvice()`, prompt in `buildCaptureAdvicePrompt()`, cached on the entry itself as `mt.advice`; filter/palette strategy and a relative integration split — no dates, no total hours, see My Targets below). Target selection is never AI. Two modes — "assisted" (direct Claude API calls from browser via `callClaudeAPI()`, requires `anthropic-dangerous-direct-browser-access: true` header) and "non-assisted" (copy/paste prompts via `#modal-copy-paste`, works with any LLM; both AI cards fall back to a "copy prompt / paste response" flow instead of a direct button). Max tokens: 1024 for AI Description, 1024 for Capture Advice, 512 for each Fetch specs call (raised from 500/600/256 on 2026-09-28, see below). `callClaudeAPI()` holds a Screen Wake Lock (`acquireWakeLock()`/`releaseWakeLock()`) for the duration of the request so the screen doesn't sleep mid-call on mobile; silently no-ops where the API is unavailable.

**Model selection** (added 2026-09-28): the model id is no longer hardcoded — Settings → AI Configuration, when in Assisted mode, shows a **Model** dropdown (`getClaudeModel()`, stored in `sap_claude_model`, default `DEFAULT_CLAUDE_MODEL = 'claude-sonnet-4-6'` until the user picks one). **Load models**/**Refresh list** button (`fetchAvailableModels()`) calls `GET https://api.anthropic.com/v1/models` with the user's key and caches the result in `sap_claude_models` (`{id, name}[]`); on first load it auto-selects the newest returned model. All three call sites read the model via `getClaudeModel()` — do not hardcode a model id again. `fetchSensorSpecs()`/`fetchTelescopeSpecs()` **route through `callClaudeAPI()`** rather than calling `fetch()` directly (fixed 2026-09-28 — they used to bypass it and were silently missing from `sap_usage_log`/Settings → API Usage). Any future direct-to-Claude call must go through `callClaudeAPI()` for the same reason: it's the only place usage logging, the model id, and the wake lock are wired up.

**Crash fixed (2026-09-28)**: `callClaudeAPI()` used to return `d.content[0].text` unconditionally, which threw `undefined is not an object` on some models/responses — reported with the model the user picked via the new selector (a "5.5"-generation Sonnet) on the AI Description card, reproduced by simulating a response whose only content block was `{type:'thinking', ...}` with `stop_reason:'max_tokens'` (no `text` block at all, i.e. the whole token budget was spent on internal reasoning before any visible output). Fixed by scanning `d.content` for the first `{type:'text'}` block instead of assuming index 0, and throwing a clear `Model returned no text (stop_reason: ...)` error when none exists — this also generalizes to whatever future block types a model may prepend. The `max_tokens` bump above (500/600/256 → 1024/1024/512) reduces how often a reasoning-capable model exhausts the budget before producing text in the first place, but the defensive parse is the actual fix; don't revert to `content[0].text`. **Why**: an older hardcoded model (`claude-sonnet-4-6`) was found to hallucinate specs for a niche telescope (Askar 71F: 336mm instead of 490mm) that a newer/current model answered correctly when asked directly on claude.ai — since this is the owner's own API cost, they wanted the choice rather than a silently-fixed hardcoded upgrade. Cost estimation (`modelPricePerMTok()`) is an approximate lookup by family (opus/haiku/else→sonnet pricing tier) since the `/v1/models` endpoint doesn't return pricing — treat `usageLine()`'s displayed cost as an estimate for non-Sonnet models. `sap_claude_model` travels in Backup & Sync (a preference, not a secret, same as `sap_llm_provider`); `sap_claude_models` (the cached list) does not.

**External APIs** (no auth, all called from the browser):
- Wikipedia: `en.wikipedia.org/api/rest_v1/page/summary/{title}` — description + photo in the Wikipedia card (only shown if Settings → "Show Wikipedia Data"; validated with `isAstroArticle()`).
- Simbad TAP (`simbad.cds.unistra.fr/simbad/sim-tap/sync`, ADQL): two queries in `fetchSimbad()` — cross-IDs (`ids` column; entries starting with `NAME ` are common names, whitespace must be normalized) and object type / morphology / V mag / distance / radial velocity. Type codes are mapped to labels (`otypes` map). Result stashed in `window._simbad` for the AI prompt.
- CDS HiPS2FITS (`alasky.cds.unistra.fr/hips-image-services/hips2fits`): sky images (`format=jpg`) and calibrated narrowband data (`format=fits`); CORS is open. **Two hosts, same API** (`HIPS_HOSTS`: `alasky.cds.unistra.fr` then the mirror `alaskybis.cds.unistra.fr`, added 2026-10-06): on 2026-10-06 the primary's HiPS2FITS *hung without any answer* (no error, other CDS services and even the primary's static HiPS tiles were fine, and the mirror answered in ~1 s), so the Framing image just spun forever — not an app bug, but the app had no timeout. Now `loadSkyFrameImage()` tries the host in `_hipsHost` for `HIPS_TIMEOUT_MS` (12 s) then the other, and remembers whichever worked for the rest of the session; if *both merely time out* it shows "The sky image service (CDS) is not responding right now" and skips the colour→red survey fallback (switching survey cannot fix an outage), while a real error on both still tries that fallback and ends on "Image unavailable". `fetchHipsFits()`/`fetchFitsPixels(url, timeoutMs)` (Emission Lines, 20 s `AbortController` timeout) and the My Targets `<img data-hips onerror="hipsImgFallback(this)">` thumbnails (`watchHipsImages()` also swaps host after 12 s if a visible one never loads) use the same two hosts. `sw.js` `IMG_HOSTS` includes the mirror so its images are cached too. Any new HiPS2FITS call must build its URL with `hipsImageUrl()` and go through one of these paths — never hardcode a host. HiPS ids used: `CDS/P/DSS2/color`, `CDS/P/DSS2/red` (both full sky), and `simg.de/P/NSNS/DR0_2/{halpha,oiii,sii}` (Northern Sky Narrowband Survey, Rayleighs, ~65% of sky, license CC BY-NC-SA — credited in Settings → About and help; keep non-commercial). NASA SkyView was tried and dropped (no "DSS2 Color", "Too Many Processes" overloads).
- **Telescopius community-photo images were tried and reverted** (an optional "Our Image / Telescopius" toggle in the Framing card, with a Settings API key field): implemented and briefly confirmed working end-to-end (CORS requires the Telescopius API key to be created as "Access Type: From a browser/website" with the app's origin in a CORS whitelist field, which took roughly an hour to propagate on their end), but the owner judged it not useful in practice — a gallery of community photos next to Framing isn't what was wanted, and Telescopius's own telescope simulator appears to apply some undocumented filtering (by image scale/rotation) to pick a *matching* community photo that the plain `/pictures/search?object_name=` endpoint doesn't replicate, so the photos shown were often a poor match for the actual framing. **Do not reintroduce this without an explicit ask.**

**Object schema**: `{id, type, ra, dec, name?, alias?, maj?, min?, pa?, con, con_full, related?}` — coords in J2000 degrees, sizes in arcminutes, PA in degrees. `con`/`con_full` = IAU constellation (short/full). `related` = array of IDs of nearby objects of same type (matched by adaptive coordinate proximity).

**`build_catalog.py`**: Fetches from VizieR classic API + OpenNGC GitHub. Deduplicates by merging specialized catalog entries with NGC/IC cross-IDs. Run once with `python3 build_catalog.py` (uses only stdlib, no pip dependencies). Produces `catalog.json`.

## Target Selection (local, no AI)

Targets are selected from `catalog.json` using weighted random sampling (`generateTargetList()`). **The search has no equipment/FOV concept at all** — it only takes a location, a period, and type/visibility criteria; equipment only enters the picture later, per-target, in the Framing card (see below). This was a deliberate simplification: with Framing letting you preview any of your equipment against the real sky per target, an equipment-based FOV coverage filter at search time was redundant and was removed, along with the "Must fit in FOV" checkbox and the FOV min/max sliders in New Target List, and the "Default FOV Coverage" min/max fields on Equipment (`coverage_min`/`coverage_max` are gone from the schema). **Do not reintroduce equipment or FOV coverage into the search/New Target List modal** without an explicit ask.

1. **Declination pre-filter**: reject objects where `90 - |lat - dec| < 20°` (instant, eliminates ~40-60%)
2. **Type filter**: exclude types with slider = 0
3. **Weighted sampling**: random without replacement, weighted by type slider values (0-10)
4. **Visibility check**: `calcWeeklyVisibility(ra, dec, lat, lon, start, numWeeks, horizonSectors, minAlt)` — keep objects with at least one week that is not `—`, then the **usable hours filter** (`Usable at least [H] h/night on at least [N] week(s)`, defaults 3 h / 2 weeks, hours 0 disables; saved in queries as `min_hours`/`min_weeks`), then optional **In season only** (≥2 weeks rated GD or EXC)
5. **Must-include**: search catalog by `id` and `alias` (case-insensitive), added before random sampling

The search period is a free number input of 1–12 weeks (`getDuration()`), so a 1–2 week search acts as a "next target" mode. The minimum altitude and horizon mask come from the selected **location** (there is no altitude slider in the search modal anymore). Saved queries (`getCurrentQuery()`/`applyQuery()`) no longer carry `equipment`/`fov_min`/`fov_max`; the query card shows the location name instead of an equipment name. The New Target List title (`generateTargetList()`) is built from months/year/Bortle/**location name**, not equipment.

**9 type sliders**: Emission Nebula, SNR, IFN, Reflection Nebula, Planetary Nebula, Galaxy, Open Cluster, Globular Cluster, Dark Nebula.

Default filters assigned per type via `TYPE_FILTERS` (e.g., emission → Hα/OIII/SII, galaxy → LRGB).

## Visibility Calculation

Uses the astronomy-engine library. `calcUsableHours(ra, dec, lat, lon, date, sectors, minAlt)` samples the target every 15 min during astronomical night (sun below -18°, via `SearchAltitude`) and counts the time when altitude ≥ `minAlt` **and**, if a horizon mask is active, the azimuth falls in a visible sector. `calcWeeklyVisibility()` evaluates one night per week (the middle one) and rates it by **usable hours**: ≥4 h → EXC, ≥2 h → GD, >0 h → MGN, 0 → `—`. Results carry `hours`. (The old altitude-based rating and the per-week "eye" indicator were removed: the mask is now folded into the badge itself.)

**Horizon mask**: `location.horizon_sectors` = 8 booleans `[N, NE, E, SE, S, SW, W, NW]`; sector index = `floor(((az + 22.5) % 360) / 45)`. All-true or missing = mask inactive. Edited with the clickable compass rose in the location form (`toggleHorizonSector()`); shown read-only as a small rose on location cards. Altitude is a per-location `min_altitude` (default 35°).

**Longitude convention**: stored as signed decimal (negative = West, positive = East). Passed directly to astronomy-engine. Display uses `Math.abs()` + N/S/E/W suffix.

`calcMaxAltDuringAstroNight()` is no longer used by the weekly visibility (kept in the file, also used nowhere else); `dayOfYear`/`objectBestDayOfYear`/`isInSeasonRange` are unused leftovers from a first "in season" attempt.

`calcBestSeasonData(ra, dec, lat, lon, minAlt)` (extracted from the old `renderBestSeason`) returns the raw per-month `{month, hours, maxAlt}` array; `renderBestSeason()` turns it into the full labeled chart, `miniBestSeasonSVG(data)` into a small unlabeled bar chart (12 thin bars, best month in green) used on My Targets list cards.

## My Targets (replaces the old session-plan/Favorites concept)

**Why**: dated, multi-target session plans (old "Select for plan" + "Generate plan") were dropped — the owner judged that weather makes date-bound integration plans unreliable and high-maintenance in practice, and that a "next target" search (1–2 week `getDuration()`) already covers short-term planning. Favorites (the ☆/★ star) were folded into the same replacement rather than kept as a separate concept. **Do not resurrect dated session plans or the Favorites star without an explicit ask** — this was a deliberate simplification, not an oversight.

**Model**: a My Targets entry is a saved **framing** — catalog object + exact framing center/angle + the **specific equipment it was framed with** + the **specific site it was planned for** (neither equipment nor site can be changed after saving: the FOV rectangle and the visibility data are meaningless without them — same reasoning for both, see "Why: a fixed site" below). Stored in `sap_mytargets`, each entry: `{id, catalog, name, type, ra, dec, angle, equipment_id, location_id, filters, size_arcmin, size_min_arcmin, pa, status, advice?, added_at, updated_at}`. `status` is `'todo' | 'in_progress' | 'done'` (segmented control, editable from both the list card and the detail screen) — a "tag" system beyond these three fixed statuses was requested for later, not built yet.

**Why a fixed site (added 2026-10-01)**: `location_id` was missing from the original model — a My Targets entry fixed its equipment but silently rode on whatever location happened to be active (or a session-only "preview" override, see below), with nothing persisted. The owner's actual intended use of My Targets clarified this was wrong: it's not a favorites list, it's **the planning tool that gives "Astro Planner" its name** — a target you intend to shoot, with a specific telescope, from a specific site (e.g. a backyard in Quebec vs. a rented observatory in Texas), looked up again once you're ready to start a session. Both equipment and site need to be fixed facts on the entry for that to work, exactly like equipment already was. Resolved via `getMtLocation(mt)`: looks up `mt.location_id`, falling back to the active location (with a "(legacy, site not fixed)" label) for entries saved before this field existed.

**Adding an entry**: only from a search-result Target Detail screen, via "+ Add to My Targets" (`addToMyTargets(tid)`) — reads the *current* `window._sky` state (post-drag/rotate), the equipment selected in the Framing card, and `getListLocation()` (the site the search itself was run for) for `location_id`. Always creates a new entry (never overwrites) — reframing the same catalog object with a different lens, angle, or site is a deliberate, distinct entry; the button shows a soft hint ("N framings already saved") rather than blocking. If an emission-line analysis exists for that catalog ID (`sap_lines[catalog]`), it's copied into the new entry's key (`sap_lines['mt:'+id]`) as a head start.

**My Targets tab** (`renderMyTargets()`, tab id still `plan`): a flat list of cards — vignette (`myTargetVignetteUrl()`, a small HiPS2FITS fetch from the saved ra/dec, same URL scheme as the Framing card so it shares the `sap-images` cache), mini Best Season (`miniBestSeasonSVG`, using **the entry's own fixed site** via `getMtLocation(mt)`), status control, Remove. Card subtitle now also shows the site name (or "⚠ site removed" / "(legacy)"), alongside the type and equipment. Tap opens the entry in the (shared) Target Detail screen.

**Target Detail in "My Targets" mode**: `openTargetDetail(tid, mtId)` — pass `mtId` to view/edit a saved entry instead of a search result (`isMt` branch throughout the function). Differences from the search-result mode:
- Equipment is fixed and shown as text, not a `<select>` (the Framing-on-Sky equipment picker is hidden).
- Weekly Visibility and Altitude Profile use **today + 12 weeks**, not a search period (there is none), and **the entry's own fixed site** (`getMtLocation(mt)`) rather than the search list's location. **Removed 2026-10-01**: the swipeable "preview other locations" cycler (`window._mtPreviewLocId`, `cycleMtPreviewLoc(dir, mtId)`, ‹ › next to the Best Season title) that used to stand in for a missing fixed site — now that the site is a real fixed fact on the entry, previewing other sites doesn't make sense (same reasoning as not letting you preview other equipment). Don't reintroduce it.
- Dragging/rotating the frame **auto-saves** back into the entry (`persistMtFrame()`, called from `updateSkyInfo()` and `setSkyAngle()`) — there is no explicit save step.
- Emission-line analysis is keyed by `'mt:'+mtId` instead of the catalog ID (`window._sky.linesKey`, set in `initSkyFrame()`; `analyzeFraming()`/`renderLinesBox()` are otherwise unchanged, just read/write through this key) — two entries framing the same object independently track their own measurement.
- A **Capture Advice** card (`renderCaptureAdvice()`/`askCaptureAdvice()`) replaces the old plan-generation flow: prompt is target + fixed equipment + FOV + Bortle + emission-line data only, explicitly **no dates, no weather, no total integration time** — asks for a filter/palette recommendation and a *relative* integration split (percentages, not hours). Cached as `mt.advice = {text, html, date}`; non-assisted mode reuses `#modal-copy-paste` (`saveCaptureAdviceFromPaste()`) the same way AI Description used to.
  - **Tried and reverted (2026-09-29)**: asking the AI for a minimum recommended angular separation from the Moon per filter. Added, then tested by regenerating the same target 3 times: results were `[35,50,40]`, `[30,40,30]`, `[30,45,35]` (Hα/OIII/SII-ish order) — no stable value, the AI was producing a plausible-looking number each time rather than applying a consistent rule (compare to the Askar 71F telescope-spec hallucination — same failure mode: confident but ungrounded specificity). Telescopius, for comparison, shows fixed values (55° for Hα/SII, 85° for OIII) that are almost certainly a static built-in table, not a per-target calculation. **Do not re-add this to the prompt** without a different approach — e.g. a hardcoded table keyed by filter bandwidth (see Out of Scope) instead of asking the LLM.
- Status segmented control + Remove button replace the old star/"Select for plan" button row.
- Prev/Next nav cycles through `sortedMtIds` (all My Targets entries) instead of `sortedTargetIds` (the current search result list).

`window._detailMtId` / `window._detailEq` are set at the top of `openTargetDetail()` in both modes and read by `buildTargetInfoPrompt()` (AI Description) so its FOV line and emission-line lookup are correct even in My Targets mode, where `getListEquipment()` would otherwise return the wrong (list-level) equipment.

**Removed entirely** (do not reintroduce without an explicit ask): `calcImagingData()` (twilight/transit/moon-phase precompute for a dated plan), the Plan Parameters modal, `buildPlanPrompt()`/`generatePlan()`/`savePlanFromText()`, the archived-plans catalog (`sap_plans`, `renderPlans()`/`viewPlan()`/`archivePlan()`/`deletePlan()`), the Favorites star and its modal (`sap_favorites`, `openFavoritesModal()`/`generateFavoritesList()`), and the target-list multi-select mechanism (`selectedTargets`, the FAB "Generate plan (N)" button, swipe-to-select on target pills, the row checkbox). `exportPlanPDF()`/`planPrintHTML()` (the print-a-new-tab PDF mechanism) were kept dormant/generic for a possible future "export Capture Advice to PDF" — parked, not wired up.

## Framing (Framing Simulator, formerly "Framing on Sky")

Card in the target detail (`#sky-frame-card`, still named after "sky" internally), shown only when an equipment configuration exists and Settings → "Show Framing Simulator" is on (`sap_preferences.skyview`; Wikipedia's toggle is `.wiki`). Placed directly under Weekly Visibility, above Altitude Profile — this is now the **only** framing preview in the app (see below).

**The old catalog-size framing card was removed** (`framingPreviewSVG()`, `navigateFraming()`, `framingTouchStart/End()`, the `framingVariants` swipe-between-related-objects mechanism, `window._framingVariants/_framingIdx/_framingFov`) — it compared the catalog's `maj`/`min`/`pa` size fields to the equipment FOV in an abstract SVG rectangle, which the owner found redundant now that Framing shows the real sky image, and actively misleading when Simbad/catalog size data is wrong or missing. **Do not reintroduce it** without an explicit ask. The Altitude Profile card (`#alt-profile-card`) that used to sit beside it in a flex row is now a full-width card by itself. State lives in `window._sky` (`t, fov, hips, angle, ra, dec, wdeg, token, drag, measuring, mtId, linesKey`) — `initSkyFrame(t, fov, mtOpts)` takes an optional `{mtId, ra, dec, angle}` to open in My Targets mode (see My Targets above).
- Image: HiPS2FITS 900×600 JPG, TAN, north up / east left, view width `wdeg = clamp(fov.w×2.2, target×1.6, 0.6..10)°` (`skyViewDeg()`); the FOV rectangle is an SVG overlay at the same pixels-per-degree, rotated by the "Camera angle" slider (no refetch).
- **Panning**: dragging moves the `<img>` visually (rectangle stays centered); on release `skyOffsetToRaDec()` (inverse TAN) computes the new center and a new image is loaded "soft" (old image stays until the new one is ready). Verified sub-pixel accurate. "Reset to target" restores the catalog center. The image container uses `touch-action:none`, so page scrolling must start outside the image.
- **Equipment selector** (if >1 equipment): changes `S.fov` and `wdeg` and reloads; does not touch the target list. Center and angle are kept.
- **Survey**: Color / Red toggle. Default is Red for Emission Nebula, SNR, Planetary Nebula (the red plate shows Hα nebulosity much better) and Color otherwise; the user's choice is remembered per target type in `sap_preferences.skySurvey`. If Color fails to load it falls back to Red without overwriting the preference.
- **Sky image "Automatic / On demand" (added 2026-10-07)**: Settings → Preferences → "Sky image in Framing" (`sap_preferences.skyLoad`: `'auto'` default, or `'demand'`; `setSkyLoadMode()`, saved immediately like the other network toggles). Motivation: many targets are so small in the user's frame that the downloaded image was useless, and CDS asks for sparing use of HiPS2FITS. `window._sky.imageOn` is `true` from the start in auto mode; in `'demand'` mode `loadSkyFrameImage()` returns early (bumping `S.token`) and calls `showSkyPreview()` instead of fetching: no HiPS2FITS request at all, the `<img>` stays hidden, a **Load sky image** button (`loadSkyImageNow()`, with `onpointerdown="event.stopPropagation()"` so the box's pointer-capture drag handler doesn't swallow the click) sits at the bottom of `#sky-frame-msg`, and `skyPreviewSVG()` (inside `drawSkyOverlay()`, only while `!S.imageOn`) draws the target as a dashed outline from its **catalog** `size_arcmin`/`size_min_arcmin`/`pa` with the same `skyRaDecToOffset()` projection and `S.wdeg` scale the image would have, plus a label "Target X · about N% of the frame width" (+ "tiny in this frame" when both axes are < 14 px, or "size unknown" with a crosshair marker when the catalog has no size — 1.5% of objects, mostly reflection nebulae and planetary nebulae). Dragging still works on the blank preview (the outline group `#sky-preview-g` is translated during the drag, then the new center is applied on release) and so do the camera angle, the equipment selector and What's in my Frame?. `imageOn` becomes `true` on the button, or automatically when `skyImageCached()` finds the exact URL already in the `sap-images` cache (checked for both CDS hosts), and then behaves exactly like Automatic for that target (drag/equipment/survey changes reload); opening another target resets it per the preference. **Deliberately not built**: a "Smart" mode that auto-loads when the target fills ≥ N% of the frame — it would again make an automatic decision from catalog sizes of uneven reliability (the reason the old min-FOV-fill filter was removed) plus an arbitrary threshold. In on-demand mode a wrong catalog size only costs one extra click, never a hidden rejection. My Targets thumbnails are unchanged (small, cached).
- **Emission Lines in Frame** (`analyzeFraming()`, on demand only): fetches the three NSNS bands as 300×200 FITS at the same center/`wdeg`, parses them client-side (`fetchFitsPixels()`), keeps pixels inside the rotated frame rectangle (`frameMask()`), and computes mean and 98th percentile per band (Rayleighs). `recommendPalette()` picks LRGB (all faint) / HOO / SHO / bicolor / single line using constants `LINE_MIN_R`, `LINE_PEAK_MIN_R`, `LINE_STRONG` (25% of the strongest), `LINE_WEAK` (10%) — initial estimates, expected to be tuned. Result saved per catalog ID with the frame it was measured in; if the frame later differs it is shown dimmed with a warning until re-analyzed. Mean is used for relative tiers (dilution by empty sky affects all bands equally), p98 for the "very faint" test.
- **"What's in my Frame?" (added 2026-10-01)**: on touch, long-press on the sky image (`skyPointerDown/Move/Up`, a `setTimeout` of `WIF_LONGPRESS_MS`=500ms armed on pointerdown, canceled on >`WIF_LONGPRESS_MOVE_PX`px movement so it doesn't fight the existing drag-to-pan) fires `skyLongPressFire()`. **On mouse the timer is never armed** (`skyPointerDown` checks `e.pointerType !== 'mouse'`) — holding the mouse button down to drag-pan would otherwise also satisfy the long-press delay, firing both at once; mouse instead uses a plain `dblclick` listener (`skyDblClick()`). Both paths converge on `skyOpenWifAtClientPoint(clientX,clientY)`, which converts the screen position to RA/Dec via the existing `skyOffsetToRaDec()` (no negation needed — unlike panning, this is a direct point query, not a delta) and calls `openWhatsInFrame(ra,dec)`. `findObjectsAtFrame()` scans `SAP_CATALOG` for objects whose angular separation from that point is within `max(their own maj/min radius, a tolerance that scales with the current view width)` — a simple circular hit-test (not a true rotated-ellipse test) chosen deliberately, since catalog `pa`/size data is sometimes wrong (see Local Database note) and a generous circle is more forgiving than a precise but brittle test; the current target itself is excluded by catalog id. Results render as amber ellipses (`wifOverlaySVG()`, using the new `skyRaDecToOffset()` forward TAN projection — the inverse of `skyOffsetToRaDec()`, with ellipse rotation derived from the catalog `pa`, standard North-through-East convention) drawn in `#sky-frame-svg` **outside** the camera-angle-rotated `<g>` (object positions are true sky geometry, unlike the FOV rectangle which represents sensor rotation) alongside a sorted-by-size list in `#wif-box` (below the image, inside the same card — deliberately not a covering modal, so the highlighted ellipse stays visible while browsing the list). Selecting a list item (`selectWifItem()`) just restyles its ellipse; **"+ Add"** (`addWifToTargetList()`) builds a target via the same `catalogToTarget()`/`calcWeeklyVisibility()` used by `generateTargetList()`, using the **current search's own site and period** (`getListLocation()`, `sap_target_meta.period_start`/`numWeeks`/`min_altitude`) so it behaves exactly as if the object had come from that search, appended to the end of `sap_targets`; already-present catalog ids show a disabled "In list ✓" instead of duplicating. **Scoped to search-result Target Detail only** (`!isMt` / `!S.mtId`), not My Targets — the owner's own framing is explicitly "no equipment/FOV concept at all" in My Targets beyond the entry's own fixed framing, so there's no search-period context to attach a new target to there. `drawSkyOverlay()` is now also called after panning/reset (previously only after angle/equipment changes) so the amber ellipses stay correctly positioned if the user drags the frame while the list is open — harmless no-op for the FOV rectangle itself, which is always screen-centered regardless of `S.ra`/`S.dec`.
  - **Stale nav/list bug fixed (2026-10-01)**: adding via "+ Add" updated `sap_targets` but not the detail screen's own `‹ › N / total` header (built once, from the `sortedTargetIds` module global, at the top of `openTargetDetail()`) nor the Targets tab underneath (`closeTargetDetail()` only toggled the overlay's CSS class, never re-rendering what was already drawn behind it) — so the new target was invisible until an unrelated full reload. Fixed two ways: `refreshTargetDetailNav()` (called from `addWifToTargetList()`) recomputes `sortedTargetIds` via the now-shared `sortTargetsForList()` (extracted out of `renderTargets()`, so the two never drift) and patches the nav buttons/counter in place, without a full detail re-render (which would reset the Framing card's scroll/zoom state); `closeTargetDetail()` now also calls `renderTargets()`/`renderMyTargets()` (by `window._detailMtId`) so the list tab is never stale when you back out of it, regardless of what changed it. `window._detailTid` (new, alongside the existing `window._detailMtId`) tracks the currently-open search-result id so `refreshTargetDetailNav()` knows what to re-locate in the refreshed order.

## Backup & Sync

Settings → Backup & Sync: `exportBackup()` writes `sap-backup-YYYY-MM-DD.json` (`version: 2`) containing `sap_locations`, `sap_equipment`, `sap_meridian`, `sap_mytargets`, `sap_saved_queries`, `sap_saved_lists`, `sap_ai_desc`, `sap_lines`, `sap_preferences`, `sap_mode`, `sap_llm_provider`, `sap_active_location`, `sap_active_equipment`. **Not exported**: the API key (`sap_claude_key`), `sap_usage_log`, the working list (`sap_targets`/`sap_target_meta`), last export/import times. Uses `showSaveFilePicker` when available, else a download (iOS Safari opens the file in a tab → Share → Save to Files).

`importBackup()` merges, never replaces wholesale:
- locations / equipment / Night Info → `mergeByUpdatedAt()` (an item missing `updated_at` counts as older than one that has it);
- `sap_mytargets` → `mergeByUpdatedAt()`, same as locations/equipment; saved queries, saved lists → added by `id` if unknown (existing local ones are kept as is);
- `sap_ai_desc` / `sap_lines` (maps keyed by catalog ID) → the entry with the newest `date` wins;
- preferences → shallow merge (imported wins) with `skySurvey` merged per type;
- `sap_mode` is applied only if the imported value is `assisted` AND the device already has an API key; active location/equipment are applied only if the device still has the default/no choice and the imported id exists locally.
Deletions do not propagate. The temporary file `<input>` must be appended to the DOM or iPhone Safari ignores it. Last export/import times are shown in Settings. Cloud sync (Supabase etc.) was deliberately not built — hosting other people's data would create responsibility; JSON files cover the personal multi-device use case.

## In-App Help (added 2026-09-29)

**Why**: as the app grew (My Targets, Framing, Moon thresholds, model choice…), the owner judged that `help.html` alone was getting harder to fully absorb for a less experienced user, without wanting to bloat the UI with per-feature explanations. Two separate, complementary features, deliberately not one:

1. **Contextual quick help (`openHelpPopup(sectionId)`, free, no AI, no network beyond `help.html` itself)**: a small circular `?` button (`helpBtn(id)`, class `.help-btn`) next to a card's title — currently on Weekly Visibility (`#visibility`), Framing (`#framing`), Altitude Profile (`#altprofile`), Best Season (`#bestseason`), the My Targets tab header (`#mytargets`), the Night Info tab header (`#meridian`), and Settings → Backup & Sync (`#backup`) — opens `#modal-help-popup` showing **the matching section of `help.html` itself**, extracted client-side, not re-explained by an AI. `getHelpDoc()` fetches `help.html?v=${HELP_VERSION}` once (cached in `_helpDoc`, a parsed `DOMParser` document) and `extractHelpSection(doc, id)` clones the `<h2 id="...">` matching that section plus every following sibling up to the next `<hr>` or `<h2>` (so h3 subsections, notes and figures under that heading come along automatically — e.g. the Framing button's popup includes its "Emission Lines in Frame" h3 too). The image paths inside (`help-img/...`) resolve fine since the popup is shown from `index.html` at the same site root. `.help-popup-body` in the main stylesheet is a hand-duplicated, scoped copy of `help.html`'s own CSS rules (h2/h3/p/ul/.note/tables/badges/figure) — **not** a reused/injected copy of `help.html`'s `<style>` block, because that block's selectors are unscoped (bare `h2`, `p`, `ul`, etc.) and would clobber the main app's own styling if inlined directly. If `help.html`'s visual style changes, `.help-popup-body`'s rules need updating to match by hand.
   - **`HELP_VERSION` constant**: the `?v=` query string used for `help.html` was pulled out of `renderHelp()` into one shared `const HELP_VERSION = '4.4'` — bump *this* (not two separate literals) whenever `help.html` changes, alongside the usual `CACHE_NAME` bump in `sw.js` and the `ASSETS` array entry there (still a separate literal, `sw.js` can't `import` the HTML's constant).

2. **Ask AI (free-form question box, `openAskAi()`/`submitAskAi()`, floating `❓` button fixed bottom-right on every tab, `#ask-ai-fab`)**: a single global entry point — deliberately **not** a proliferation of per-feature "ask AI about this" buttons, which the owner judged wouldn't add much over the static popup above (an AI just re-explaining a paragraph the user could already read, with more room to hallucinate). This is for open-ended questions a fixed doc section can't answer directly ("how do I prioritize narrowband on full moon nights" — spans target selection, filters and Moon thresholds at once). Grounded in **`help.html`'s plain text** (`getHelpPlainText()` — `doc.body.textContent`, so `<style>`/images are excluded automatically since `DOMParser` keeps `<style>` in `<head>`) **plus the full text of `CLAUDE.md`** (`getDevNotes()`, fetched as plain text, cached in `_devNotes`) — concatenated into one prompt (`buildAskAiPrompt()`) instructing the model to answer only from that material and to keep dev-notes jargon out of the answer unless truly relevant. Same assisted/non-assisted branching as everywhere else: assisted calls `callClaudeAPI()` directly (so it's counted in `sap_usage_log` and uses whatever model the user picked); non-assisted reuses `#modal-copy-paste` (a generic "paste the response, show it" flow — `showAskAiPasteResponse()` — unlike Capture Advice's version, nothing is saved anywhere, it's a one-off Q&A, not tied to a target).
   - **Cost is real and was measured, not guessed**: `help.html` plain text ≈ 7,400 tokens, `CLAUDE.md` ≈ 10,750 tokens, ≈ 18,000 tokens of input per question on Sonnet pricing ≈ **$0.05/question** — confirmed via a mocked API response during testing (18,040 tokens → $0.05 reported). Raw `index.html` JS (~45–60K+ tokens) was considered and rejected for this reason — `CLAUDE.md` already exists as a dense, maintained summary of the same mechanics and costs a fraction as much to send.
   - **`CLAUDE.md` must now be deployed alongside the other files** (like `help-img/`) — it's fetched at runtime by `getDevNotes()`, not just read by Claude Code during development. It contains no secrets, and the app's own JS is already fully visible client-side anyway, so this isn't a new exposure. Do not rename the actual repository file to something else for this purpose — Claude Code itself auto-loads project guidance specifically from a file named `CLAUDE.md` at the project root, so renaming it would break that for future sessions; the file simply now serves two audiences.
   - **Images are deliberately excluded** from what's sent to the AI — confirmed unnecessary during design: the model only needs the textual mechanics/rationale, not the screenshots.

## Key Patterns

- `font-size: 16px` on ALL inputs/selects/textareas — prevents iOS auto-zoom
- `normalizeVis()` handles multiple visibility string formats
- Target selection: swipe on pill (mobile), checkbox (desktop via `@media(hover:hover)`). Tap anywhere on row opens detail.
- FOV/plate scale computed locally from equipment data via `calcFOV()`, never stored.
- Moon sensitivity via `moonSensitivity()`: all narrowband → insensitive, all broadband → sensitive, mixed → partial. Reflection/IFN/Dark Nebula/Globular Cluster always broadband-sensitive.
- No default location is seeded on first run (`sap_locations` starts as `[]`) — the AstroPeak Observatory default was removed 2026-09-28; `openNewTargets()` guards against zero locations with a "Add a location first" toast + redirect to the Locations tab, same pattern as the equipment guard. The location form's lat/lon placeholders show Quebec City's coordinates (46.813 / -71.208), not real values.
- Equipment form has an AI "Fetch specs" lookup for both the sensor (`fetchSensorSpecs()`, fills width/height/pixel size/resolution) and the telescope (`fetchTelescopeSpecs()`, fills focal length/aperture) — same pattern, both call the Claude API directly and only show when a Claude API key is set (`hasKey`). Best-effort: if the AI can't identify the model, the user fills the fields manually.
- `help-img/` holds the screenshots used in `help.html` (11 JPGs, ~0.5 MB, lazy-loaded, cached by the service worker on first view; **must be uploaded with the other files**). They use DEMO data only (never the owner's real home coordinates) and are regenerated with `tools/help-screenshots/make_shots.sh` (headless Edge + a scripted demo scene in `shot.js`; `tools/` is not part of the deployment; any file the app loads at startup — e.g. `astronomy.browser.min.js`, which silently broke every demo scene until added — must also be symlinked in the script's file list). Regenerate after visible UI changes; crop boxes are hard-coded in the script. Known gap: in the altitude fullscreen modal the chart keeps its 300×140 aspect and leaves empty space on tall screens.
- `help.html` versioned via query string (currently `?v=4.0`). When help changes, update the version in both `sw.js` (ASSETS array) and `index.html` (`renderHelp()`), and bump `CACHE_NAME` in `sw.js`.
- Plan export (`exportPlanPDF(id)`): builds a standalone print-ready HTML document (`planPrintHTML()`) and opens it via `window.open(blobURL, '_blank')` from directly inside the click handler (no `await` before it, to preserve the user-gesture). **Do not switch this back to `window.print()` on the main document** — iOS/iPadOS disables the print API for an installed PWA in `display: standalone` (see manifest.json), so the button would silently do nothing; opening a separate tab escapes standalone mode and printing works there. If `window.open` returns falsy (popup blocked), a toast asks the user to allow pop-ups. The old `@media print` block on the main page's `.plan-content`/`#tab-plan` is unused dead CSS, kept for now.
- Framing preview SVG (the original small card): rectangle at scale with PA rotation. Both FOV and target drawn at same arcmin-to-pixel ratio. The sky-image Framing Simulator (above) is a separate, larger card.
- FOV coverage: surface area ratio `(target area) / (FOV area) × 100`. Optional "Must fit in FOV" checkbox combines with min/max sliders.
- Target list sorted by type (in slider order) then alphabetically. Type abbreviations shown in column: Em, SNR, IFN, Ref, PN, Gal, OC, GC, Dk.
- Date parsing uses `split('-')` instead of `new Date(string)` to avoid UTC timezone shift. Getting "today" as a `YYYY-MM-DD` string must go through `todayLocal()` (`getFullYear()`/`getMonth()`/`getDate()`, all local) — **never** `new Date().toISOString().slice(0,10)`, which is UTC and silently returns tomorrow's date for part of the evening in any timezone west of UTC (e.g. ~8pm–midnight in UTC-4/EDT). This actually happened: the backup filename and the New Target List default start date were both wrong for that window before `todayLocal()` was introduced. All "today" call sites route through it now (`grep todayLocal()`); a new one must too.
- Wikipedia lookup validates results against astronomy keywords to avoid false matches.
- Altitude Profile / Best Season track the **current framing center**, not the static catalog position: `window._detailLoc`/`window._detailStartDate` are set once at the top of `openTargetDetail()` (both search-result and My Targets modes), and `recalcSkyDependent()` re-runs `updateAltChart()`/`renderBestSeason()` against `window._sky.ra/dec` (the live, possibly-dragged framing) every time `updateSkyInfo()` fires — i.e. after a drag or "Reset to target". `updateAltChart(ra, dec, ..., weekIdx, ..., dayIdx)` is called with `weekIdx`/`dayIdx` as `null` so it keeps whatever week/day the user was viewing rather than jumping back to week 1. Rationale: a target reframed far from its catalog center (e.g. switching from a 500mm to a 135mm scope and dragging to catch something in a corner) is genuinely a different point in the sky, and the altitude/season should reflect that. **Weekly Visibility badges are NOT recalculated this way** — they're still computed once from the static catalog `t.ra`/`t.dec` at render time; only Altitude Profile and Best Season follow the live framing. Extend to Weekly Visibility too only if asked — it would need restructuring since the badges are concatenated into `html` once rather than refreshed from a dedicated container.
- Target Detail swipe navigation: swipe left/right anywhere in `#detail-content` (`detailTouchStart/End()`, `>60px` horizontal and horizontal-dominant over vertical) clicks `#detail-next-btn`/`#detail-prev-btn` — safe at list boundaries since those buttons have `onclick = null` when disabled, so `.click()` is a no-op. Excludes `#alt-chart-swipe`, `#sky-frame-box`, and any `input[type=range]` (checked via `e.target.closest()` in `detailTouchStart`) since those already own horizontal gestures (week/day toggle, drag-to-reframe, slider dragging — both the camera-angle slider and `#alt-chart-slider` are outside `#alt-chart-swipe`'s bounds, so the range-input rule is what actually protects them, not the container selectors). Extend the selector, not a hardcoded list of ids, if a future card adds its own horizontal drag that isn't a `<input type=range>`. The header's `‹ ›` buttons (desktop) are unchanged and still work standalone.
- Altitude Profile fullscreen (long-press/double-click opening `#modal-alt-full`, with `_syncAltSliders()` mirroring state into a second set of DOM elements) was **removed** — the card is full-width now that the old catalog-size Framing card is gone, so it wasn't worth the duplicated-DOM-sync complexity. `altChartTouchStart/End()` do plain swipe detection only (`>40px` triggers `navigateAltDay()`); there is no `altChartTouchMove` and no long-press timer. **Watch for this class of bug if re-touching this code**: an earlier version had a `touchmove` handler that set a "moved" flag to cancel the long-press timer, but that same flag also gated the swipe logic in `touchend` — since any real swipe exceeds the moved-threshold, it silently broke swipe navigation entirely (arrows still worked). Don't reintroduce a flag shared between two purposes like that.
- Night Info tab (`sap_meridian`): saved targets with exact framing center, showing transit time, signed time remaining and nautical/astronomical dusk→dawn per target location (`calcTransitTime()`, `calcNightTimes()`). Coordinates are entered compactly (RA `HHMMSS`, Dec sign toggle + `DDMMSS`) with live preview. Used to verify the Stellavita meridian flip. **Scope, clarified 2026-10-01**: Night Info is short-lived, session-specific scratch data — added once you start actively shooting a target, deleted again a few days/weeks later once you no longer need it; it just answers "what time can I start tonight/this week." It is *not* a second My Targets and should not grow planning features (status, equipment, long-term tracking) — that's what My Targets is for. An entry has no dedup/update-in-place logic by design (`saveMeridianTarget()` always `push`es a new `{id: uuid(), ...}` when called without an `editId`) — sending the same framing twice creates two identical entries; considered adding duplicate detection, but dropped once the real fix turned out to be giving My Targets a fixed site (see My Targets below) rather than Night Info needing to be smarter.
- **"+ Night Info" button** (`addToMeridianFromTarget(tid, mtId)`, one of `tid`/`mtId` is null): present in **both** Target Detail modes now (fixed 2026-10-01 — it only existed in search-result mode before, not My Targets, the opposite of what the owner remembered when asked). Prefers the **live framing center** (`window._sky.ra/dec`, i.e. wherever the Framing card is currently dragged to) over the static catalog/`mt` position — this was the actual original ask ("send the moved frame's center to Night Info"), previously it always sent the static `t.ra`/`t.dec` regardless of dragging. Falls back to the catalog position (search mode) or the saved `mt.ra`/`mt.dec` (My Targets mode) when `window._sky` is absent or belongs to a different target (no equipment configured, Settings → Show Framing Simulator off, or a stale object left over from a previously-viewed target) — verified via `S.mtId === mtId` / `S.t?.id === tid` before trusting it, so the button never silently no-ops.
- Toast wording for imports must always report something ("Already up to date" when nothing changed) or users think the import failed.
- Filter name is `'Hα'` (Greek alpha, not ASCII `'Ha'`) everywhere in `TYPE_FILTERS` and target data — `FILTER_COLORS` map and other lookups must key off `'Hα'` (kept as alias `'Ha'` too for hand-typed equipment filters).
- Shared color helpers: `filterBadges(filters)` (colored pill per filter, used in Target Detail, Equipment list/form) and `bortleColor(bortle)` (green→red scale 1-9, used in Locations list/form). Defined near the top of the script alongside other small helpers.
- Desktop visual treatment pattern (cards get a subtle border + hover lift + accent-colored `.card-title`, mobile/tablet get a static border only) is applied via `.device-desktop`/`.device-phone`/`.device-tablet` scoped selectors per page (Target Detail, Equipment, Locations, their Add/Edit forms, Settings, Plan Parameters modal). **Not** applied to the Plan tab itself (active/archived plan list) — that was tried and reverted, left in its original unstyled form.
- Form sections in modals use `.form-section` (bordered box with an icon+accent `<h3>`) — pattern shared by Add/Edit Equipment, Add/Edit Location, the Favorites modal, and Plan Parameters.
- Altitude Profile detail chart overlays the Moon's angular separation from the target (dashed line, same 0-90° axis as altitude, dash pattern denser as the Moon phase nears full) on top of the existing altitude curve. Each of the two curves' end-labels independently flip above/below their own line based on that line's own value (>75° → label below) — they do NOT react to each other, so occasional visual overlap between the two curves in extreme cases is accepted as a known limitation, not a bug to chase further. The chart has two independent controls: the slider moves through weeks (default) or, once toggled, through the 7 days of the selected week; swipe/‹›-arrows only flip between week-mode and day-mode (either direction flips it) and never move the slider's position themselves.
- **Per-filter Moon separation badges under the Altitude Profile** (redesigned 2026-10-06; this replaced a colored Moon line + a Narrowband/Broadband selector, see below). Settings → Preferences has 4 optional number fields (Hα, OIII, SII, Broadband — one shared value for L/R/G/B, not per-channel, per the owner's own framing "superflu d'avoir un minimum par filtre") stored in `sap_preferences.moonThresholds = {Ha, OIII, SII, broadband}` (degrees; blank = absent). `updateAltChart()` draws the Moon distance as a plain neutral dashed line again and fills `#alt-moon-legend` — placed **above** `#alt-chart-slider` in the card (a finger dragging the slider on a phone would otherwise cover the badges) — with **one badge per filter of the target's own equipment** (`window._detailEq.filters`, same pill look as `filterBadges()`, filter name only: the threshold is in the `title` tooltip, because the number made 7 badges wrap to two lines on an iPhone; the explanatory key lives in the static note below the slider) via `moonFilterStatus(filters, thresholds, nightPts)` / `moonThresholdFor()`: **full color** = the Moon is ≥ the filter's threshold at every point of the astronomical night (`astroSet`→`astroRise`, falling back to all chart points if there is no astronomical night), **dashed + faded + ◐** = only part of the night (the usable time ranges are listed underneath, grouped by identical ranges), **grey** = never. Filters whose threshold is blank are not drawn and are named in a "Not shown" line; with no applicable threshold the legend is empty (opt-in, as before). A summary line gives the Moon's real min–max distance that night. Because the legend is built inside `updateAltChart()`, the badges follow the slider in both week and day mode with no extra wiring. **Comparisons use `points[].moonDistRaw`**, never `moonDist`: `moonDist` is capped at 90° to fit the chart axis, which silently made any threshold above 90° (typically Broadband) impossible to satisfy in the first version.
  - **Why the colored line was dropped (2026-10-06)**: the first version colored the line by "the most demanding filter still usable", which read as an error to the owner — Hα's own badge color is red and sat right next to the dark-red "none usable" color, so a perfectly shootable Hα/SII night looked like a bad one; it also could not express several narrowband filters with different thresholds or both families at once. A per-filter on/off badge answers "which filters can I shoot tonight?" directly. The Narrowband/Broadband selector (`sap_preferences.moonBasis`, `setMoonBasis()`) was removed with it (the badges already show both families side by side); a leftover `moonBasis` in stored preferences is harmless. Do not go back to encoding filter state in the line's color.
  - **Tried and reverted, same session**: asking the AI (Capture Advice prompt) for a minimum Moon separation per filter, instead of a user-configured value — see the "Crash fixed" note above's sibling entry for why (regenerating the same target 3× gave `[35,50,40]`/`[30,40,30]`/`[30,45,35]`, no stable value). The Settings-based version here exists because a fixed, user-owned number is exactly what that attempt was missing.
  - **Considered and declined (2026-10-01)**: pre-filling the 4 Settings fields with suggested default values (a small hardcoded table, à la Telescopius's fixed 55°/85°) instead of leaving them blank. Owner judged the need already met by manual entry — not worth sourcing defensible per-filter defaults for. Don't add default values without a new ask.

## Running Locally

No node_modules needed. Serve with any HTTP server:
```
python3 -m http.server 8080
```
Do NOT open `index.html` via `file://` — fetch for `catalog.json` and Claude API calls will fail. The custom server in `.claude/launch.json` (used by the preview tool) does not strip query strings, so `catalog.json?v=5` **and `astronomy.browser.min.js?v=…`** 404s (the latter leaves `Astronomy` undefined, so every visibility calculation throws) and the service worker install fails there: for anything that computes visibility, use `python3 -m http.server` instead; otherwise inject the catalog manually (`SAP_CATALOG = await (await fetch('/catalog.json')).json()`) when testing, or use `python3 -m http.server`.

- **Tag system for My Targets**: beyond the fixed To do / In progress / Done status, free-form tags were requested ("on y reviendra") to help decide what to prune once the list grows — not designed yet. Confirmed still wanted (2026-09-27), backlog.
- **Mosaic framing support** (rows × columns × overlap %, tiled grid in the Framing card instead of a single rectangle): explored 2026-09-29, explicitly deferred ("on oublie la mosaic, peut-être dans une version future") — not rejected, just not now. Open design questions flagged during exploration, to revisit if picked up: whether overlap is one % for both axes or separate H/V values; `skyViewDeg()`'s 10° view-width cap would need raising (or accepted as a partial visual) once the mosaic footprint exceeds it; whether Emission Lines in Frame measures only the center/reference panel (simple, less representative of edge panels) or the whole mosaic footprint (coarser per-pixel resolution at the same 300×200 FITS fetch size).
